Role: You are a Senior QA Automation Engineer and System Analyst with expertise in Laravel, multi‑tenancy, and attendance/payroll systems. Your task is to thoroughly verify the recent code changes in the attendance module (specifically AttendanceCalculator and HandlesAttendanceRecord) and ensure they meet the requirements, fix multi‑tenancy issues, and do not introduce regressions.

Objective
Validate that:

Multi‑tenancy is correctly enforced – employees only see policies, shifts, work patterns, and shift schedules belonging to their own company.

Attendance calculation logic is correct – status, hours, overtime, breaks, lateness/early departure are computed according to the assigned policy.

Special cases (holidays, approved leaves, unplanned absences) are handled properly.

Performance is acceptable (no N+1 queries, caching works).

No regressions are introduced in existing functionality.

Environment Setup
Use a fresh copy of the staging database with at least two companies (e.g., Company A and Company B).

Create two employees – one in Company A, one in Company B.

Create separate attendance policies, shifts, work patterns, and shift schedules for each company (with overlapping IDs if possible to test isolation).

Use test data that includes:

Clock‑in/out events for several days.

A holiday date.

An approved leave request.

A day with no events (to test unplanned absence).

Test Cases
1. Multi‑Tenancy Isolation
ID	Description	Steps	Expected Outcome
MT‑01	Employee from Company A sees only Company A policies	1. Fetch applicable policy for Employee A using AttendanceCalculator::getApplicablePolicy().
2. Check that returned policy has company_id = Company A.	Policy belongs to Company A. No policy from Company B returned.
MT‑02	Employee from Company A sees only Company A work patterns	1. Fetch work pattern for Employee A using AttendanceCalculator::getApplicableWorkPattern().
2. Verify company_id.	Work pattern belongs to Company A.
MT‑03	Employee from Company A sees only Company A shifts and schedules	1. Run getExpectedSchedule() for Employee A.
2. Check that any shift or shift schedule returned belongs to Company A.	All shifts have company_id = Company A.
MT‑04	Cross‑company policy assignment is ignored	1. Create a PolicyAssignment for a shift in Company B.
2. Assign that shift to Employee A (should not be possible normally, but if it exists, test that getPolicyForEntity() filters by company).	The policy assignment is not returned for Employee A because company_id filter excludes it.
2. Attendance Calculation Accuracy
ID	Description	Steps	Expected Outcome
AC‑01	Normal day – on time, full shift	1. Provide clock‑in at shift start, clock‑out at shift end.
2. Run calculateForDay().	Status = present, net_hours = shift duration, regular_hours = shift duration, no lateness or early departure.
AC‑02	Late arrival (beyond grace period)	1. Clock‑in 15 minutes after shift start.
2. Run calculation.	Status = late, minutes_late = 15, regular/overtime hours adjusted accordingly.
AC‑03	Early departure (before shift end, beyond grace)	1. Clock‑out 20 minutes before shift end.
2. Run calculation.	Status = early_departure, minutes_early_departure = 20, hours reduced.
AC‑04	Overtime (daily)	1. Work 10 hours on an 8‑hour shift, with policy threshold 8h and overtime multiplier 1.5.
2. Run calculation.	regular_hours = 8, overtime_hours = 2, double_time_hours = 0 (if threshold not met).
AC‑05	Double‑time (if configured)	1. Work 13 hours, with double‑time threshold 12h.
2. Run calculation.	overtime_hours = 4 (12‑8), double_time_hours = 1 (13‑12).
AC‑06	Unpaid break deduction	1. Policy has unpaid_break_minutes = 30.
2. Work 8 hours, clock‑in/out accordingly.
3. Run calculation.	net_hours = 7.5, regular_hours = 7.5 (or adjusted), break_deduction noted in metadata.
AC‑07	Break compliance (missed break)	1. Work 6 hours without a long enough gap (break). Policy requires break after 5h, 30min.
2. Run calculation.	Status may be present but missed_break_minutes = 30, violation recorded.
AC‑08	Half‑day	1. Work 4 hours on an 8‑hour shift.
2. Run calculation.	Status = half_day, net_hours = 4, regular_hours = 4.
AC‑09	Absent	1. No clock events on a work day.
2. Run calculation.	Status = absent, net_hours = 0, needs_review = true.
3. Special Cases
ID	Description	Steps	Expected Outcome
SC‑01	Company holiday	1. Insert a holiday record for the date.
2. Employee has no clock events.
3. Run recalculateForDay().	Status = holiday, net_hours = 0, sessions cleared.
SC‑02	Approved leave	1. Create an approved leave request for the date.
2. Run calculation.	Status = leave, net_hours = standard hours (e.g., 8), regular_hours = 8, leave_request_id linked.
SC‑03	Unplanned absence	1. No clock events, no holiday, no leave.
2. Run calculation.	Status = absent, is_unplanned = true, needs_review = true, hours_deducted set to standard hours.
4. Performance & Caching
ID	Description	Steps	Expected Outcome
PF‑01	Caching reduces DB queries	1. Run getPolicyForEntity() twice with same parameters.
2. Monitor query log.	The second call does not hit the database (cache hit).
PF‑02	Bulk recalculation performance	1. Recalculate 30 days for 10 employees (simulate via script).
2. Measure time and DB query count.	Time should be reasonable (< 5 seconds) and no N+1 queries.
5. Regression Testing
ID	Description	Steps	Expected Outcome
RG‑01	Existing data not corrupted	1. Run recalculateForDay() for a date that already has an attendance record.
2. Verify that the record is updated, not duplicated, and sessions are refreshed.	Attendance record updated, old sessions replaced.
RG‑02	UI data table still shows correct records	1. Open the Attendance list view.
2. Ensure company filter (from session) works as before.	Data table shows records only for the selected company.
RG‑03	Manual adjustments (AttendanceAdjustment) still work	1. Manually adjust an attendance record.
2. Later, run recalculation for that day.	The adjustment history is preserved (if soft‑delete not used, this may need separate handling, but at least the adjustment record remains).
Testing Procedure
Set up test data using seeders or factories.

Execute each test case by calling the appropriate methods (e.g., via Tinker or unit tests).

Inspect the database to confirm values.

Log all queries to verify company filters are applied (use Laravel Debugbar or query log).

Run unit/integration tests if available.

Report any failures with clear steps to reproduce.

Expected Output
Provide a test report summarizing:

Pass/Fail status for each test case.

Screenshots or logs of query execution (showing where company_id = ... clauses).

Performance metrics (if applicable).

Any edge cases discovered that were not covered.

Additional Notes

Verify that policy_assignments are correctly filtered by company_id.

If you encounter any ambiguity, refer to the business rules document or ask the development team.

Success Criteria
All critical test cases (MT‑01 to MT‑04, AC‑01 to AC‑09, SC‑01 to SC‑03) pass.

No cross‑company data leakage occurs.

Performance is within acceptable limits.

No regression in existing functionality.
